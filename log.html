Candidate directions

claude's proposals, not facts. ranked: my recommendation first. bora picks or rejects. rt-j is read from its project page only [rtj-6].

  • [dir-1] controlled study of relational priors at nano scale. proposal
    • what: rebuild the rdb-pfn recipe in modded-nanotabpfn. vary one thing at a time: generator (single-table / plurel / rdb-pfn), DFS setting, amount of data.
    • new: nobody has separated prior quality from data scale. plurel-to-rdb-pfn names this as its open question [p2r-4]. rdb-pfn's ablations use 20k databases only [rdbpfn-6].
    • new: evaluation in the relarena protocol (full train split by chunked context, same data state), not few-shot only.
    • first experiment: train the small model on rdb-pfn's released generator, reproduce one few-shot number of the paper.
    • risk: reads as a replication if no clear finding comes out. the model is small, so absolute scores stay below tabpfn-rel.
    • fit for march 2027: good. small models, your own training code, 1 GPU.
  • [dir-2] a prior with forecasting tasks. proposal
    • what: synthetic databases where the label is an aggregate over a future time window, per entity, at several seed times. like relbench [relbench-3].
    • new: rdb-pfn and plurel-to-rdb-pfn use a random column as target [rdbpfn-5] [p2r-3]. no time-window labels, no repeated entities.
    • new: regression targets. 9 of 21 relarena tasks are regression; rdb-pfn has none [rdbpfn-4].
    • why it can matter: tabpfn-rel adds target lags by hand, and a per-entity constant is a strong baseline [relarena-8]. the prior could teach this.
    • first experiment: dir-1 setup + one change (window labels). compare on the rel-f1 tasks.
    • risk: needs dir-1 first. the gain may be small.
    • fit for march 2027: ok as the second half of dir-1. too much as a start.
  • [dir-3] cheaper flattening. proposal
    • what: find which DFS features and depths carry the signal; prune or sample before the feature pass.
    • new: relarena names this as future work: depth 2 is already competitive, DFS costs CPU hours [relarena-5] [relarena-6].
    • first experiment: per-feature-group ablation on cached depth-4 matrices of 3 small tasks.
    • risk: an engineering result, less of a foundation-model thesis.
    • fit for march 2027: good. also a direct contribution to the prior labs repo.
  • [dir-4] learned flattening: set encoders in place of DFS, trained on a synthetic prior. proposal
    • what: adapters on a frozen TFM that pool child rows, like graphpfn does for graphs [graphpfn-2].
    • new: removes interaction blindness with training; relicl does it without training [relicl-2].
    • risk: openrfm already joins RT blocks with a tabicl layer [openrfm-2]. highest engineering cost.
    • fit for march 2027: poor.
  • [dir-5] a tabular model trained on real flattened relational tables. proposal
    • what: run DFS on the 639 databases of THE JOIN [rtj-2] and continue the pretraining of a small PFN on these flat tables. compare with the synthetic priors of dir-1.
    • new: rdb-pfn says real relational data is too scarce for this [rdbpfn-1]. THE JOIN removes that reason. the question "synthetic relational prior vs real flattened data" is then testable.
    • risk: the corpus is new; download size, licences and DFS cost on 639 databases are unknown. unverified: nobody did this is my guess from 14 papers.
    • fit for march 2027: ok as one arm of dir-1, not alone.
  • [dir-0] warm-up, not a thesis: boosted trees on DFS features in relarena. proposal
    • relarena lists it as a missing baseline [relarena-7]. small, a pull request to prior labs, and it teaches the harness. fits stage 2 and 4.
  • my recommendation: dir-0 as the first week, dir-1 as the core, dir-2 as the contribution on top. not now: dir-3, dir-4.

formal definition (for talk part 2)

  • source: fey et al. 2023 "relational deep learning", §2.1-2.2 (papers/rdl/src/problem-formulation.tex L22-33, L57-61). the rdl-survey §2.1 repeats it (tex/020dataset.tex L20-27). relbench has no formulas, it describes the same thing in words (sections/design.tex L13-14).
  • [formal-1] database. (𝒯, ℒ). tables 𝒯 = {T₁, …, Tₙ}. links ℒ ⊆ 𝒯 × 𝒯. a link L = (T_fkey, T_pkey) exists if a foreign key column in T_fkey points to the primary key of T_pkey. (rdl L22)
  • [formal-2] row = entity. each table is a set T = {v₁, …, v_{n_T}}. each entity v = (p_v, 𝒦_v, x_v, t_v): primary key, foreign keys, attributes x_v = (x_v¹, …, x_v^{d_T}), optional timestamp. (rdl L23-33)
  • [formal-3] task = training table. T_train with entities v = (𝒦_v, t_v, y_v): keys of the entities the example is about, timestamp (relbench calls it seed time), label. the training table has no inputs x_v. it is attached to the database: 𝒯 ∪ {T_train}, ℒ ∪ ℒ_{T_train}. (rdl L57-58)
  • [formal-4] temporal constraint. to predict y_v the model may only use entities u with t_u ≤ t_v. (rdl L61)
    • detail: rdblearn uses strictly earlier, t_u < t_v (rdblearn sections/04_rdblearn.tex L83). relarena says the boundary is not standardized between methods [relarena-7].
  • [formal-5] label generation. labels come from the database itself: a time-conditioned SQL query over the window [t, t+δ], then t is moved back in fixed steps to get more examples. (rdl L55, L85)
  • [formal-6] task types. node-level: columns (EntityID, Label, Time). link-level: (SourceEntityID, TargetEntityID, Label, Time). (rdl L78-80)
  • [formal-7] the in-context view, for tabpfn-rel. notation of rdblearn §2 (sections/02_background.tex L95-102; 03_recipe.tex L14-25):
    • per-task supervised: f_θ(x_test, RDB) ≈ y_test
    • in-context: y_test = f_θ(x_test, 𝒟_ICL, RDB), with 𝒟_ICL = {(x_i, y_i)}
    • flattening: u = g(𝒩_RDB(x)), z = [x; u], y_test = f_θ(z_test, 𝒟^z_ICL). g is fixed and not learned. the database reaches the model only through g.
    • note: rdblearn writes RDB = (𝒯, ℛ), fey writes (𝒯, ℒ). same thing. i use ℒ in the talk.

relarena-alpha (hayler et al. 2026, arxiv 2608.16319) - read fully

file: papers/relarena-alpha/src/main.tex

  • [relarena-1] what it is. a harness on the 21 relbench v1 entity tasks: same data loading, same evaluation regime, tuning run by the harness, aggregation with tabarena's bencheval (Elo). 3 releases: relarena, tabpfn-rel, RPI (yaml task specification). (L85-89, L296, L331)
  • [relarena-2] why published numbers are not comparable (§1, L104-283)
    • evaluation regime: relbench freezes the database at the test cutoff for all test rows. kumorfm-2 and the RT family let each test row see data up to its own timestamp. only rel-f1 is affected: there test timestamps span 3 to 6 years. effect: more than 10 AUC points on the two f1 classification tasks, more than 40 % MAE on the regression task. (L232-234)
    • data state: relbench fixed a temporal leak in rel-event/user-ignore in early 2026. re-run scores are 2 to 6 AUC points lower than the old published ones. (L241)
    • tuning: relgnn checkpoints imply a grid of over 25,000 configurations, kumorfm-2 384, undocumented. relgnn and relgt compare tuned models against the untuned relbench RDL numbers. (L218, L251)
    • aggregation: every paper normalises regression MAE differently, or reports R². several drop 3 to 6 of the 21 tasks. (L258)
    • baselines: tabular baselines got only the entity table's own columns. in relbench v2 the lightgbm baseline received only NaN at test time (50 % AUC). (L271-274)
  • [relarena-3] methods run. model submissions: tabpfn-rel (API, with text), tabpfn-rel (OSS, no text), rdblearn v1 (without limix), graphsage, relgt, relgnn. plus trivial lightgbm (entity columns + timestamp only) and two constant predictors. system submission: rt-plurel. (L379-384)
  • [relarena-4] result. tabpfn-rel is first among models. rt-plurel is first when systems are included. single seed. (L402-411, L379)
    • rt-plurel = the 85M-parameter RT (12 blocks, dim 512), plurel-pretrained checkpoint, then fine-tuned per task: up to 50,000 steps, muon, lr 5e-4, batch 256, weight averaging, early stopping; then 60 context configurations scored on validation; test = 8 context seeds averaged. (app. E, L628-669)
    • per-task test scores: results_analysis/tables.tex. rt-plurel is best on 5 of 12 classification tasks and 5 of 9 regression tasks. tabpfn-rel (API) is best on 3 + 1, tabpfn-rel (OSS) on 1 + 2. (my count of the bold cells)
    • Elo, joint board with self-reported numbers: tabpfn-rel (API) 1851, graphsage (relarena) 1714, relgt (relarena) 1605, relgnn (relarena) 1503, lightgbm 1365, constant per-entity 1262, constant global 1000. relgnn self-reported is 1949: about 450 points higher than its re-run. (results_analysis/selfreported_elo.tex)
  • [relarena-5] tuning. each configuration is fit on the inner split (database frozen at the val cutoff), scored on validation; the best is refit on the outer split. (L524) tabpfn-rel tunes only DFS depth, 3 configurations. tuned beats default on 9 of 21 tasks (API), same on 7, worse on 5. depth 2 "remains competitive with the deeper configurations". (L447, L612-618)
  • [relarena-6] cost. runtime table excludes preprocessing (L548-566). per task, median: tabpfn-rel OSS 4 min, API 88 min, rdblearn 7 min, graphsage 35 min, relgt 273 min, rt-plurel 231 min. DFS preprocessing is CPU-bound and "can often take hours per dataset" (L533). limit 24 h per task (L539). caches are allowed; cache scripts must be public (L535).
  • [relarena-7] limits they name themselves.
    • one seed (L379)
    • timestamp boundary: GNN baselines and rt-plurel use rows at the entity's test timestamp as context when cutoff and timestamp align; tabpfn-rel and rdblearn do not. "this might disadvantage the latter". (L464)
    • no boosted trees on DFS features yet: "we do not yet report baselines that lift traditional tabular learners … through automated feature engineering". (L459)
    • tuning budgets are not matched in compute (L387, L521)
    • conflict of interest: benchmark and top model from the same group; they state it (L390)
  • [relarena-8] constant-per-entity (each entity's own best constant from its training labels) beats relgnn and relgt on 4 tasks each. only tabpfn-rel and rt-plurel beat it on all 21. on rel-stack/post-votes almost no method is clearly better than the constant. (L431)
  • [relarena-9] text: OSS (no text) vs API (text): Elo 1706 vs 1821. the gap comes from rel-event/user-ignore (0.7014 vs 0.8787 AUC) and rel-avito/user-clicks (0.6145 vs 0.6752). (L426-427, tables.tex)
  • numbers to reproduce in stage 2 (test, tabpfn-rel OSS / lightgbm): rel-f1/driver-top3 0.7929 / 0.7389 AUC; rel-f1/driver-dnf 0.7145 / 0.7303; rel-f1/driver-position 3.762 / 4.106 MAE. (tables.tex). f1 is the smallest database.

tabpfn-rel - paper + code

  • [tabpfnrel-1] recipe (relarena §2.2, main.tex L351-361): DFS along all key paths up to depth d → one flat table, one row per (entity, cutoff) → tabpfn-3 predicts the test rows in-context from the train rows. d ∈ {2, 3, 4}, chosen on validation.
  • [tabpfnrel-2] changes vs rdblearn (L355-361): database frozen at the val cutoff while tuning; tabpfn-3 as the only backbone, with 10× more context rows; text columns of the entity table re-attached (API only); recency-aware context; validation rows added to the context for the test prediction.
  • [tabpfnrel-3] code, from your fork, read only:
    • default config: tfm "tabpfn-v3", context_strategy "hard_pool", subsample_samples K = 100,000 per estimator, pool_inflation 4.0 (pool M = 4·K most recent rows), with_text False. grid = depth 2, 3, 4, depth 2 first. (relarena-pr:src/relarena/models/tabpfn_rel/model.py:47-66)
    • 8 estimators by default for the pool strategies; each draws K rows from the pool without replacement. (…/tabpfn_rel/context.py:34, 85-102)
    • DFS max depth 4, computed once and sliced for depth 2 and 3 (feature sets are nested). engine: fastdfs, dfs2sql, duckdb. (relarena-pr:src/relarena/featurization/dfs.py:5, 30-34, 64, 579)
    • before DFS: datetime columns → epoch floats; text columns dropped. after DFS: absolute time features → difference to the row's cutoff. (dfs.py:13-22)
    • target history: a table of past labels is injected into the database before DFS, joined strictly before the cutoff. (dfs.py:24-28)
    • extra features after DFS: sin/cos of month, day of week, day of year of the cutoff; per-entity lags of the target; raw text for the API. (…/tabpfn_rel/features.py:1-17, 31-35)
    • the list of aggregation functions is not in relarena. it comes from fastdfs defaults. fastdfs default: max, min, mean, std, count, mode [repo-fastdfs-1]. the same 6 as rdblearn.
  • [tabpfnrel-4] feature count. rdblearn on rel-f1/driver-top3, unbounded depth: 7,715 columns before pruning, 5,460 after. the schema has 67 columns. (relicl 02-dfs.tex L82-86)

relicl (forbat and gemulla 2026, arxiv 2610.01725) - read fully

  • [relicl-1] two limits of DFS (main-sections/02-dfs.tex)
    • feature explosion: width = O(#meta-paths · #attributes · #aggregates). practical fix = depth bound; featuretools 1.31.0, rdblearn 1.1 and tabpfn-rel all use depth 2 by default. (L78-96)
    • proposition: for every depth bound there are tasks DFS cannot solve. synthetic test, label stored 3 hops away: rdblearn 50.8 % AUC, relicl 100 %. (L98-114)
    • interaction blindness: each DFS feature aggregates one column. synthetic test where only the correlation between two columns of the child rows carries the label: rdblearn = random. (L156-178)
    • their own limit statement: these are synthetic tasks; on relbench "DFS models may nevertheless perform well". (04-experiments.tex L177-180)
  • [relicl-2] method (main-sections/03-methodology.tex)
    • assumption: a TFM run on its own row embeddings is as good as on the raw table. tested with tabicl on 10 openml tables: 8 of 10 lose at most 1.5 AUC points; philippine loses 8.9, jasmine 3.0. (L54-76; appendix/method.tex L97-104)
    • 3 phases: outward pass marks the relevant rows; inward pass runs the TFM encoder on each table, pools the row embeddings into the parent rows (sum / mean / max + a count column; temporal pooling excludes future rows); final TFM prediction on the extended task table. (L100-180)
    • no depth bound. width of the extended task table depends on the number of direct neighbour tables only. (L174-177)
    • tricks: gaussian random projection of embeddings 512 → 32; sub-sampling of large tables; leaf tables joined in; junction tables split in two. (04-experiments.tex L45-52; appendix/method.tex L13-30, L58-62)
  • [relicl-3] evaluation. 21 entity tasks, "relbench v2". backbone tabicl v2 (default), also tabpfn v3. one global configuration + small ensemble (2 members regression, 4 classification). 11 hyperparameters found by random search, 100 trials per task on 6 + 6 of the 21 tasks, 121 GPU-hours. (04-experiments.tex L16, L77-94; appendix/setup.tex L59-62, L122-124)
  • [relicl-4] result claim. "on par with" tabpfn-rel, ahead of rdblearn, RT and plurel in pairwise wins. baseline numbers are copied from the papers, not re-run. (04-experiments.tex L155-162, L171-174). this is the practice relarena criticises [relarena-2]. i did not open the generated result tables.
  • note: 12 of the 21 tasks were used to choose the default configuration, on validation data (appendix/setup.tex L60-62).

rdb-pfn (wang et al. 2026, arxiv 2603.03805) - read fully

file: papers/rdb-pfn/src/example_paper.tex

  • [rdbpfn-1] what it does. synthetic database → DFS → one table → nanotabpfn-style transformer → in-context prediction. "Linearize-and-Attend". (L159, L506-528)
    • baselines (tabpfn v2.5, tabicl v1.1, mitra, limix16m) get "the exact same linearized DFS features". so the comparison is: same input, different prior. (L566)
    • claim "Prior > Scale". (L168)
  • [rdbpfn-2] the prior, 3 stages. P(D) = P(schema graph) · P(keys, links, latent row states | schema) · P(feature columns | structure). (L343-355)
    • assumptions: schema graph is a DAG (they say over 95 % of spider + 4dbinfer schemas are acyclic, L309); a value depends only on a k-hop neighbourhood (L321-331); rows of a table are exchangeable given the links (L335-339)
    • stage 1, schema: LayerDAG, a discrete diffusion model for DAGs, trained on real public schemas (spider, bird). (L392, L992-997). so "purely synthetic" holds for the table contents, not for the schema topology. ablation: a simple DAG generator is "slightly" worse (L997).
    • stage 2, links: "selective SCM". each new child row gets a latent z, scores M candidate parent tuples with query-key attention, samples one from the softmax. (L397-422; alg. 1, L1005-1021). optional feedback update of the chosen parent → between uniform and preferential attachment. (L424, L1027-1035)
    • time: the latent init can depend on timestamp features: trend, seasonality, spike. (L1037-1048)
    • stage 3, content: random bidirectional GNN on the row graph, K rounds, sum per key type, shared MLP decoder → column values. continuous = clip / normalise, categorical = binning. (L430-450)
  • [rdbpfn-3] DFS setting. aggregations Mean, Max, Min, Count, Mode. parent attributes copied. default 2-hop. (L1073-1075, L1225)
  • [rdbpfn-4] model. 6 layers, d_model 128, 4 heads. 0.7M parameters (L460, L584, L1057-1061). alternating feature attention and row attention (L524-528). binary head only; multi-class "can" go one-vs-rest; no regression (L530, L672, L877-881).
    • conflict: the released config has width 96, not 128 [repo-rdbpfn-1].
    • conflict: plurel-to-rdb-pfn describes the same backbone (6 layers, 128 dims, 4 heads) as 2.6M parameters (plurel-to-rdb-pfn §4.1 setup, main.tex L242-250). unverified which is right; count it in the repo.
  • [rdbpfn-5] pretraining. (L1079-1133)
    • stage 1: 600k synthetic single tables, 600 rows × 18 columns, 1× RTX 4090, schedule-free AdamW, lr 5e-4
    • stage 2: about 1.8M datasets on 8× RTX 4090 = about 600k single-table + about 1.2M relational (800k small prior 1-hop, 200k small prior 2-hop, 200k large prior 1-hop)
    • DFS output over-generated (60 columns for 1-hop, 90 for 2-hop), then subsampled to 30. every stage 2 task is 600 rows × 30 columns.
    • 6 random target columns per schema. the target is a column, not a time-window label.
    • rows sampled uniformly from the DFS table.
  • [rdbpfn-6] evaluation. 19 binary tasks from 13 databases: 4dbinfer (amazon, avs, diginetica, outbrain, retailrocket, stackexchange) + relbench (amazon, avito, event, f1, hm, stack, trial). task table L787-817. few-shot only: context N ∈ {64, 128, 256, 512, 1024}, sampled uniformly from the train split, 10 seeds, ROC-AUC. (L562, L856-858, L883)
    • tree baselines: random forest 500 trees; xgboost 5000 trees, lr 0.01, depth 12; autogluon medium_quality. (L893-899)
    • RT and griffin are not same-protocol baselines. reason given: RT puts train labels into the database as a table, so its label context is local to each entity; rdb-pfn uses one global support set. (L966-970)
    • larger support only by chunking and averaging, up to 8192, "with diminishing gains". context size named "an important limitation". (L1164)
    • fine-tuning on the target task improves over strict ICL (1000 steps × 1024 samples). (L1162)
    • single-table check (grinsztajn 2022 subset, N = 1000): trails specialised TFMs. (L613)
    • ablations use 20k RDBs, not the full pipeline. (L1193)
  • [rdbpfn-7] DFS sensitivity (their table, context 1024, 7 small tasks; L1240-1243): 1-hop avg 0.5711, 2-hop 0.7330, 2-hop max/min/mode only 0.7107, 2-hop mean/count only 0.7141. they call DFS "useful but non-optimal" (L1227).
  • not in the paper, unverified, check the repo: how the DFS respects the cutoff time at evaluation; text columns.

plurel (kothapalli et al. 2026, arxiv 2602.04029) - main text + appendix A, B

file: papers/plurel/src/main.tex

  • [plurel-1] what it is. a generator of synthetic databases, 3 stages, used to pretrain RT with masked token prediction. (L249-298, L339-340 of the experiments part)
  • [plurel-2] stage 1, schema. random DAG from {barabasi-albert, reverse random tree, watts-strogatz}. tables with out-degree ≥ 1 = entity tables, others = activity tables. (§2.1; app. A.1)
  • [plurel-3] stage 2, keys. rows of child and parent table are put in a hierarchy of blocks; a hierarchical stochastic block model gives the link probabilities. 1 to 5 levels, 1 to 3 blocks per level. block matrix: 0.9 on the matching block, U(0.001, 0.002) elsewhere. (§2.2; app. A.2)
  • [plurel-4] stage 3, features. one SCM per table. a node's mechanism also takes the feature nodes of the parent tables' SCMs (through the key links). numeric or categorical with equal probability. temporal: source-node inputs = average of trend (power law), cycle (sine) and noise, indexed by row. NULL cells added. (§2.3; app. A.3)
  • [plurel-5] limits they state. no cycles and no self-links (rel-stack posts.ParentId is their example). no text. (app. "Limitations"; §2.3 data types)
  • [plurel-6] hyperparameters (table in app. A): 3 to 20 tables; 500 to 1000 rows per entity table; 2000 to 5000 rows per activity table; 3 to 40 columns (power law); timestamps 1990-01-01 to 2025-01-01; 1 to 10 % NULL cells; 2 to 10 categories; MLP hidden 32, depth 2; activations relu, elu, silu, softsign, tanh.
  • [plurel-7] pretraining of RT. 12-layer RT, batch 128, context 1024 cells, BFS width 128, AdamW, wd 0.1, peak lr 5e-4. about 3 hours per run on one B200. base model for continued pretraining: 1024 synthetic databases, 4B tokens. (experiments setup)
  • [plurel-8] evaluation. 6 relbench databases (not rel-event). zero-shot: 10 binary tasks (AUROC) and 8 regression tasks (R²). continued pretraining on real data: leave-one-database-out. (experiments setup; "continued pretraining")
  • 3 claims: pretraining loss follows a power law in the number of databases and tokens; more synthetic databases → better transfer to real ones; synthetic pretraining is a good base for continued real pretraining. (abstract). i did not check the numbers behind these.
  • difference to rdb-pfn's prior: plurel links by block model and has no learned schema model; rdb-pfn links by attention over candidate parents and uses a GNN for content. plurel makes no tasks; rdb-pfn picks target columns. (plurel-to-rdb-pfn §1 introduction)

plurel-to-rdb-pfn (abolhasani and ganapathy 2026, arxiv 2607.29129) - abstract, intro, method, setup, discussion

  • [p2r-1] plurel databases → binary tasks → rdb-pfn DFS → rdb-pfn training. about 5,500 databases, about 33k tasks, no single-table warm-up. best curriculum: 0.6346 average AUC at 1024-shot vs 0.7245 published rdb-pfn = 87.6 %. at 64-shot 0.6116 vs 0.6517 = 93.8 %. (abstract)
    • my note: 0.5 is chance for AUC. measured above chance, 0.1346 vs 0.2245 is 60 %.
  • [p2r-2] best curriculum: a real schema first (relbench rel-salt: 4 tables, 31 columns, 6 key edges, filled with synthetic rows), then fully synthetic schemas. the reverse order is much worse (0.5544 / 0.5729). (method; results)
  • [p2r-3] tasks: up to 6 target columns per database, binary columns preferred, else median split. plurel output forced to INTEGER/FLOAT. small databases: 50 to 200 entity rows, 150 to 450 activity rows. (method)
  • [p2r-4] limits they state: not scale-matched; no categorical / text; heuristic tasks; binary only. their open question: is the gap from generator quality or from data scale. (discussion)

rt (ranjan et al. 2026, arxiv 2510.06377) - abstract, contribution, method

  • [rt-1] cell = token, embedded from value + "column of table" text embedding. the task is a table attached to the database (task table prompting); prediction = masked cell. (sections/method.tex, input representation)
  • [rt-2] context: n cells around the seed row by bounded BFS over key links. parents always included, children subsampled with width w, rows later than the seed row excluded. (same section)
  • [rt-3] relational attention: column attention, feature attention (same row + parent rows), neighbour attention (child rows), full attention. no positional encodings. (same section; plurel app. B)
  • [rt-4] 22M parameters. pretrained on relbench databases. zero-shot = 90.3 % of the supervised AUROC on average, 93.1 % with continued pretraining on the target database. (sections/abstract.tex; sections/introduction.tex L56-61)
  • "in-context labels" come from task rows that fall into the BFS context. not a global support set. (sections/introduction.tex L51-53). openrfm builds on this point [openrfm-1].
  • i did not read results, analysis, appendix.

rt-j (ranjan et al. 2026, openreview oQINTd9din) - project page only

source: https://star-project.stanford.edu/rt-j, read 5 oct 2026. the pdf on openreview did not download by script (it returned a web page). every line here is from the project page, not from the paper.

  • [rtj-1] what it is. the RT architecture with a new training recipe for few-shot prediction. 85M parameters, 12 layers, hidden 512, 8 heads. one model for classification and regression. unverified (page only)
  • [rtj-2] THE JOIN. an open corpus of 639 real databases with about 6,000 forecasting tasks and 10,600 autocompletion tasks. databases that overlap with relbench are left out. tasks are proposed by a language model, checked against the schema, then filtered by a gradient-boosted model. on hugging face: stanford-star/the-join. unverified (page only)
  • [rtj-3] training. two phases: first the synthetic plurel corpus, then THE JOIN. each under a day on up to 8 B200 GPUs. released checkpoint = weight average after 9k steps of the second phase. unverified (page only)
  • [rtj-4] recipe. context length is sampled during training (up to 8,192 cells); only the target cell is masked (denser masking hurt); context rows come from short random walks from the target row. unverified (page only)
  • [rtj-5] results on relbench, 21 tasks. regression: 6 to 13 % lower relative nMAE than every label-matched in-context baseline. tuned and ensembled: 32.4 mean nMAE with a few hundred examples, vs rdblearn 31.4 with 10,000 labels, vs kumorfm-2 29.1. classification: ahead by up to 3 AUROC points when labels are scarce; the best baseline catches up at the largest budget. unverified (page only)
  • [rtj-6] what it means for the directions (my reading)
    • the strongest open relational FM now uses synthetic data only as a first phase and real data as the second. this agrees with openrfm [openrfm-2].
    • real forecasting tasks at scale now exist (THE JOIN). so "no forecasting tasks in pretraining" is true for the synthetic priors only [dir-2].
    • THE JOIN is a resource for you: 639 real schemas for the data statistics of stage 3, and real DFS-flattened tables to train or test a tabular model on.
    • rt-j targets few labels. with many labels the flattening methods are still level or ahead on classification, by their own account.

openrfm (chen et al. 2026, arxiv 2606.04320) - abstract, intro, start of method

  • [openrfm-1] two diagnoses of RT (chapters/introduction.tex, last paragraphs):
    • model: RT's failures correlate with how many label-carrying cells land in the sampled context. few label cells → an underdetermined regression.
    • data: plurel-only pretraining gives "a near-fixed, lazy kernel"; pretraining on in-distribution tasks gives a feature-learning regime. the missing part, they say: a "support-identifiable relational latent" in the label generation, realised through relational homophily.
  • [openrfm-2] fixes: RT blocks + a batch-level ICL layer taken from tabicl, so a query attends to its key neighbourhood and to all support rows in the batch; homophily-aware synthetic data + continual real-data pretraining; a prototype regulariser. claim: about 30 % better than RT on average, above kumorfm v1. (chapters/introduction.tex; chapters/method.tex start)
  • their statement on the field: "neither purely synthetic nor real-world pre-training delivers satisfactory downstream performance without task-specific continual training". (chapters/introduction.tex)
  • i did not read analysis, experiments, appendix.

graphpfn (eremeev et al. 2025, arxiv 2509.21489) - abstract, pretraining, result summary

  • [graphpfn-1] PFN for node-level tasks on one graph. prior: multi-level SBM + preferential attachment for structure, graph-aware SCM for attributes. (abstract)
  • [graphpfn-2] model: limix + attention-based neighbourhood aggregation layers ("graph adapters"). training continues from the limix checkpoint; all layers frozen except the adapters. 1,600,000 synthetic datasets, 10,000 optimizer steps, about 36 h on 8× A100 80GB, AdamW, lr 1e-3, EMA 0.98. loss = PFN loss + 0.1 × masked-edge loss. (paper.tex §3.2, L246-262)
