stage 3: what the benchmark data looks like

all 7 relbench v1 databases and the 21 entity tasks. computed by scripts/relbench_stats.py → stats/*.json; tables by scripts/stats_summary.py. relbench 2.1.2 (the version relarena pins). column kinds are my heuristic on pandas dtypes: text = strings with mean length over 30 or mostly unique values. the local relbench cache is 18 GB.

  • [s3-1] what a prior must match (my summary of the tables below; 7 databases, 50 tables, 61 key links, 21 tasks)
    • table size is very uneven: 68 to 30,386,403 rows, median about 250,000. plurel draws 500 to 5,000 rows per table [plurel-6].
    • tables are narrow: median 6 columns. one outlier with 110 columns (rel-event).
    • key links per table: 0 (17 tables), 1 (8), 2 (22), 3 (3). so most fact tables join exactly two other tables.
    • fan-out is heavy-tailed: over the 61 links, the median of "mean children per parent" is 8.1, the median of "max children per parent" is 442, the largest is 929,887. mean / median of children is about 2.1 on a typical link.
    • many parents have no child: median 40 % of parent rows; on 24 of 61 links more than half.
    • feature columns: 194 numeric, 90 categorical, 59 text, 2 bool, 1 datetime. so about 17 % is text. rdb-pfn and plurel have no text [plurel-5].
    • 16 of 50 tables have no time column (the entity / dimension tables).
    • missing values: median null fraction per table 0.002, max 0.51.
    • one self-link: rel-stack posts.ParentId → posts. the published priors cannot make this [plurel-5].
  • [s3-2] what the tasks look like
    • label balance is extreme in both directions. train positive rate: 0.039 (avito user-clicks), 0.048 (stack user-badge), 0.05 (stack user-engagement), 0.17 (event user-ignore, f1 driver-top3), 0.43 (amazon item-churn), 0.49 (event user-repeat), 0.62 (amazon user-churn), 0.64 (trial study-outcome), 0.82 (hm user-churn), 0.88 (f1 driver-dnf), 0.91 (avito user-visits).
    • regression targets are zero-inflated: 94 % zeros in stack post-votes, 81 % in hm item-sales, 72 % in event user-attendance, 62 % in amazon user-ltv, 51 % in trial site-success, 41 % in trial study-adverse.
    • the same entity repeats over seed times in most tasks: median rows per entity in train is 52 (hm item-sales), 15 (stack tasks), 9 (f1 driver-top3), 3 to 5 (amazon); it is 1 in rel-trial, avito and most of rel-event.
    • number of seed times in train: 3 (avito), 19 to 22 (trial, event), 31 (amazon), 40 to 52 (stack, hm), 59 to 420 (f1). val and test have 1 seed time each, except rel-f1 with 23 to 33.
    • window length: 4 days (avito), 7 days (hm, event), 30 or 60 days (f1), 91 days (stack, amazon), 365 days (trial).
    • the label rate shifts between train and test: avito user-clicks 0.039 → 0.015; avito user-visits 0.906 → 0.851; amazon item-churn 0.434 → 0.370; event user-ignore 0.169 → 0.130.

formal definition (for talk part 2)

  • source: fey et al. 2023 "relational deep learning", §2.1-2.2 (papers/rdl/src/problem-formulation.tex L22-33, L57-61). the rdl-survey §2.1 repeats it (tex/020dataset.tex L20-27). relbench has no formulas, it describes the same thing in words (sections/design.tex L13-14).
  • [formal-1] database. (𝒯, ℒ). tables 𝒯 = {T₁, …, Tₙ}. links ℒ ⊆ 𝒯 × 𝒯. a link L = (T_fkey, T_pkey) exists if a foreign key column in T_fkey points to the primary key of T_pkey. (rdl L22)
  • [formal-2] row = entity. each table is a set T = {v₁, …, v_{n_T}}. each entity v = (p_v, 𝒦_v, x_v, t_v): primary key, foreign keys, attributes x_v = (x_v¹, …, x_v^{d_T}), optional timestamp. (rdl L23-33)
  • [formal-3] task = training table. T_train with entities v = (𝒦_v, t_v, y_v): keys of the entities the example is about, timestamp (relbench calls it seed time), label. the training table has no inputs x_v. it is attached to the database: 𝒯 ∪ {T_train}, ℒ ∪ ℒ_{T_train}. (rdl L57-58)
  • [formal-4] temporal constraint. to predict y_v the model may only use entities u with t_u ≤ t_v. (rdl L61)
    • detail: rdblearn uses strictly earlier, t_u < t_v (rdblearn sections/04_rdblearn.tex L83). relarena says the boundary is not standardized between methods [relarena-7].
  • [formal-5] label generation. labels come from the database itself: a time-conditioned SQL query over the window [t, t+δ], then t is moved back in fixed steps to get more examples. (rdl L55, L85)
  • [formal-6] task types. node-level: columns (EntityID, Label, Time). link-level: (SourceEntityID, TargetEntityID, Label, Time). (rdl L78-80)
  • [formal-7] the in-context view, for tabpfn-rel. notation of rdblearn §2 (sections/02_background.tex L95-102; 03_recipe.tex L14-25):
    • per-task supervised: f_θ(x_test, RDB) ≈ y_test
    • in-context: y_test = f_θ(x_test, 𝒟_ICL, RDB), with 𝒟_ICL = {(x_i, y_i)}
    • flattening: u = g(𝒩_RDB(x)), z = [x; u], y_test = f_θ(z_test, 𝒟^z_ICL). g is fixed and not learned. the database reaches the model only through g.
    • note: rdblearn writes RDB = (𝒯, ℛ), fey writes (𝒯, ℒ). same thing. i use ℒ in the talk.

tabpfn-rel - paper + code

  • [tabpfnrel-1] recipe (relarena §2.2, main.tex L351-361): DFS along all key paths up to depth d → one flat table, one row per (entity, cutoff) → tabpfn-3 predicts the test rows in-context from the train rows. d ∈ {2, 3, 4}, chosen on validation.
  • [tabpfnrel-2] changes vs rdblearn (L355-361): database frozen at the val cutoff while tuning; tabpfn-3 as the only backbone, with 10× more context rows; text columns of the entity table re-attached (API only); recency-aware context; validation rows added to the context for the test prediction.
  • [tabpfnrel-3] code, from your fork, read only:
    • default config: tfm "tabpfn-v3", context_strategy "hard_pool", subsample_samples K = 100,000 per estimator, pool_inflation 4.0 (pool M = 4·K most recent rows), with_text False. grid = depth 2, 3, 4, depth 2 first. (relarena-pr:src/relarena/models/tabpfn_rel/model.py:47-66)
    • 8 estimators by default for the pool strategies; each draws K rows from the pool without replacement. (…/tabpfn_rel/context.py:34, 85-102)
    • DFS max depth 4, computed once and sliced for depth 2 and 3 (feature sets are nested). engine: fastdfs, dfs2sql, duckdb. (relarena-pr:src/relarena/featurization/dfs.py:5, 30-34, 64, 579)
    • before DFS: datetime columns → epoch floats; text columns dropped. after DFS: absolute time features → difference to the row's cutoff. (dfs.py:13-22)
    • target history: a table of past labels is injected into the database before DFS, joined strictly before the cutoff. (dfs.py:24-28)
    • extra features after DFS: sin/cos of month, day of week, day of year of the cutoff; per-entity lags of the target; raw text for the API. (…/tabpfn_rel/features.py:1-17, 31-35)
    • the list of aggregation functions is not in relarena. it comes from fastdfs defaults. fastdfs default: max, min, mean, std, count, mode [repo-fastdfs-1]. the same 6 as rdblearn.
  • [tabpfnrel-4] feature count. rdblearn on rel-f1/driver-top3, unbounded depth: 7,715 columns before pruning, 5,460 after. the schema has 67 columns. (relicl 02-dfs.tex L82-86)

  • [relicl-1] two limits of DFS (main-sections/02-dfs.tex)
    • feature explosion: width = O(#meta-paths · #attributes · #aggregates). practical fix = depth bound; featuretools 1.31.0, rdblearn 1.1 and tabpfn-rel all use depth 2 by default. (L78-96)
    • proposition: for every depth bound there are tasks DFS cannot solve. synthetic test, label stored 3 hops away: rdblearn 50.8 % AUC, relicl 100 %. (L98-114)
    • interaction blindness: each DFS feature aggregates one column. synthetic test where only the correlation between two columns of the child rows carries the label: rdblearn = random. (L156-178)
    • their own limit statement: these are synthetic tasks; on relbench "DFS models may nevertheless perform well". (04-experiments.tex L177-180)
  • [relicl-2] method (main-sections/03-methodology.tex)
    • assumption: a TFM run on its own row embeddings is as good as on the raw table. tested with tabicl on 10 openml tables: 8 of 10 lose at most 1.5 AUC points; philippine loses 8.9, jasmine 3.0. (L54-76; appendix/method.tex L97-104)
    • 3 phases: outward pass marks the relevant rows; inward pass runs the TFM encoder on each table, pools the row embeddings into the parent rows (sum / mean / max + a count column; temporal pooling excludes future rows); final TFM prediction on the extended task table. (L100-180)
    • no depth bound. width of the extended task table depends on the number of direct neighbour tables only. (L174-177)
    • tricks: gaussian random projection of embeddings 512 → 32; sub-sampling of large tables; leaf tables joined in; junction tables split in two. (04-experiments.tex L45-52; appendix/method.tex L13-30, L58-62)
  • [relicl-3] evaluation. 21 entity tasks, "relbench v2". backbone tabicl v2 (default), also tabpfn v3. one global configuration + small ensemble (2 members regression, 4 classification). 11 hyperparameters found by random search, 100 trials per task on 6 + 6 of the 21 tasks, 121 GPU-hours. (04-experiments.tex L16, L77-94; appendix/setup.tex L59-62, L122-124)
  • [relicl-4] result claim. "on par with" tabpfn-rel, ahead of rdblearn, RT and plurel in pairwise wins. baseline numbers are copied from the papers, not re-run. (04-experiments.tex L155-162, L171-174). this is the practice relarena criticises [relarena-2]. i did not open the generated result tables.

plurel (kothapalli et al. 2026, arxiv 2602.04029) - main text + appendix A, B

file: papers/plurel/src/main.tex

  • [plurel-1] what it is. a generator of synthetic databases, 3 stages, used to pretrain RT with masked token prediction. (L249-298, L339-340 of the experiments part)
  • [plurel-2] stage 1, schema. random DAG from {barabasi-albert, reverse random tree, watts-strogatz}. tables with out-degree ≥ 1 = entity tables, others = activity tables. (§2.1; app. A.1)
  • [plurel-3] stage 2, keys. rows of child and parent table are put in a hierarchy of blocks; a hierarchical stochastic block model gives the link probabilities. 1 to 5 levels, 1 to 3 blocks per level. block matrix: 0.9 on the matching block, U(0.001, 0.002) elsewhere. (§2.2; app. A.2)
  • [plurel-4] stage 3, features. one SCM per table. a node's mechanism also takes the feature nodes of the parent tables' SCMs (through the key links). numeric or categorical with equal probability. temporal: source-node inputs = average of trend (power law), cycle (sine) and noise, indexed by row. NULL cells added. (§2.3; app. A.3)
  • [plurel-5] limits they state. no cycles and no self-links (rel-stack posts.ParentId is their example). no text. (app. "Limitations"; §2.3 data types)
  • [plurel-6] hyperparameters (table in app. A): 3 to 20 tables; 500 to 1000 rows per entity table; 2000 to 5000 rows per activity table; 3 to 40 columns (power law); timestamps 1990-01-01 to 2025-01-01; 1 to 10 % NULL cells; 2 to 10 categories; MLP hidden 32, depth 2; activations relu, elu, silu, softsign, tanh.
  • [plurel-7] pretraining of RT. 12-layer RT, batch 128, context 1024 cells, BFS width 128, AdamW, wd 0.1, peak lr 5e-4. about 3 hours per run on one B200. base model for continued pretraining: 1024 synthetic databases, 4B tokens. (experiments setup)
  • [plurel-8] evaluation. 6 relbench databases (not rel-event). zero-shot: 10 binary tasks (AUROC) and 8 regression tasks (R²). continued pretraining on real data: leave-one-database-out. (experiments setup; "continued pretraining")
  • 3 claims: pretraining loss follows a power law in the number of databases and tokens; more synthetic databases → better transfer to real ones; synthetic pretraining is a good base for continued real pretraining. (abstract). i did not check the numbers behind these.
  • difference to rdb-pfn's prior: plurel links by block model and has no learned schema model; rdb-pfn links by attention over candidate parents and uses a GNN for content. plurel makes no tasks; rdb-pfn picks target columns. (plurel-to-rdb-pfn §1 introduction)

bora asked for a full read of every paper in the list. one entry per paper, added as i finish it. "read" here means the main text; i name what i left out.

  • [fr-rt] rt, read: introduction, background, method, results, ablations, conclusion (papers/rt/src/sections/*.tex). not read: related work, appendix.
    • setting, in their words: "zero-shot relational learning" = new targets on a new database with a new schema, no weight updates; the context "need not consist of explicit input-output pairs" (background §2.3). so RT is not few-shot ICL in the tabpfn sense.

    • training: 50k steps, context 1024 cells, batch 256, AdamW wd 0.1, peak lr 1e-3; fine-tuning 33k steps, lr 1e-4. about 2 h pretraining and 1.5 h fine-tuning on 8× A100. (training details)
    • data: relbench v1 forecasting tasks + autocomplete tasks they define; rel-event skipped "as it has been found to have temporal leakage issues". leave-one-database-out; the best checkpoint is chosen per target task on validation, because of "significant overfitting during pretraining due to limited pretraining tasks". (experimental setup)
    • baselines: griffin (same setup, matched parameters), gemma3 4B / 12B / 27B on serialised subgraphs, RDL-GNN, relLLM, and EntityMean = "the mean of the past labels for the target entity".

    • their own ranking of what enables zero-shot transfer (conclusion): "(1) time-series forecasting from past task rows for the target entity, (2) column attention …, (3) feature attention …, (4) schema semantics from table and column names, (5) in-context learning from task rows for other entities".
    • feature extraction: a 2-layer MLP on frozen RT embeddings is 1.6 AUROC points below full fine-tuning and 4.3 R² points above it (relational feature extraction).
    • limits they state: no recommendation / link prediction; key column names not used; two foreign keys to the same table are not told apart (conclusion).
    • meaning for us: this is the same signal as in my runs, from the other side. RT's zero-shot ability is mostly "the entity's own label history" (53.8 without it), other entities' labels add nothing (70.6 vs 70.1). tabpfn-rel builds exactly that signal as features [s4-9]. so on relbench, the relational model and the flattening methods compete on one feature family, and ICL across entities is not yet shown to matter.
  • [fr-openrfm] openrfm, read: preliminaries, analysis, method, experiments, conclusion (papers/openrfm/src/chapters/*.tex). not read: appendix (theory, plurel prior details, full tables).
    • definition they use: an RFM predicts ŷ = f_θ(x | S, D) from support rows S of the task table and the database D, in one forward pass (preliminaries). they call DFS + TFM methods "nonparametric" RFMs; JUICE is their name for the rdblearn-style pipeline (xu et al. 2026).
    • diagnosis 1, label reachability. ρ(T) = share of seed rows whose BFS walk reaches another task-table row. RT is good when ρ is high and collapses when it is low: trial study-outcome ρ = 0.002 → RT AUC 0.493 (lightgbm 0.701, JUICE 0.715); trial study-adverse ρ = 0.006 → RT R² −0.017 (JUICE 0.470); f1 driver-top3 ρ = 0.893 → RT 0.824 (JUICE 0.762). (analysis §4.1, small table)
      • this matches stage 3: rel-trial has 1 row per entity, rel-f1 has 9 [s3-2]. and it matches my rdb-pfn run, which is also worst on study-outcome [s4-8].
    • diagnosis 2, lazy regime. corruption test on the walked rows: shuffle the labels among neighbours, or permute the non-label columns. under plurel-only pretraining both changes cause "near-inconsequential drops": the model reads the support only as an average label. under in-distribution pretraining both hurt. (analysis §4.1.1, I1 and I2)
    • their explanation in PFN terms (analysis §4.2): a prior-fitted network approximates the posterior predictive ∫ p(y*|x*,z) p(z|D) dz. if the support labels carry little information about the latent mechanism z, "a lazy / fixed-kernel solution can be population-optimal". in plurel and rdb-pfn the cross-row label dependence is "hard-coded into the SCM rather than carried by … a latent" that varies per episode.
    • their fix on the data side: per database, sample a homophily target h from a grid of 20 values between heterophily and homophily, and generate the label as a mixture of a cluster-driven and a feature-driven channel so that the realised homophily follows h (range about −0.44 to +0.74). continued pretraining of RT-plurel on this corpus "restores the feature-learning regime under purely synthetic supervision".

    • what it is: a benchmark for generators that copy one real database (SDV, RC-TGAN, REaLTabFormer, clavaDDPM, two commercial tools) on 6 small databases. not priors. but its evaluation method is directly usable for a prior.
    • the method i can reuse ("discriminative detection with aggregation"): join each parent table with child-row counts, means of child numeric columns and distinct counts of child categories; label rows real / synthetic; train XGBoost with cross-validation; test the accuracy against 50 %. then read feature importance and partial dependence to see where the synthetic data differ.
    • this turns my stage 3 comparison "prior vs real" [pvr-1] from a list of summary statistics into one number plus a ranked list of the mismatching features. with flattened tables the test is: can a classifier tell DFS rows of prior tasks from DFS rows of relbench tasks. the across-dataset version needs schema-free features (per-column statistics); my extension, not in the paper.
    • their results: "no method is able to synthesize a dataset that is indistinguishable from original data". almost all methods fail the multi-table test. the most discriminating features are the relational ones (child counts, child aggregates), not the columns of the table itself.
    • error pattern: parent tables are modelled better than child tables; they suspect that errors build up along the hierarchy because children are generated given parents. plurel and rdb-pfn generate in the same parent-to-child order [plurel-3].
    • why the usual metrics are too lenient: logistic regression as detector cannot see column interactions; denormalised parent-child rows are not independent, so accuracy is above 50 % even for two real samples; "cardinality shape similarity" (KS test on children per parent) checks one aspect only.
    • utility: train on synthetic, test on real, on 3 databases with a time column. for the two regression tasks the result is "at most near the naive baseline, often much worse". model and feature rankings are not preserved well.
    • they do not use relbench: its databases "include modalities such as text, which are not supported by the generative models". sampling a representative part of a database is called an open problem.
  • [fr-reldiff] reldiff (hudovernik et al. 2025), read: introduction, related work, method, experiments text (papers/reldiff/raw.txt L1-1400). not read: ablations after table 2, appendix. earlier: abstract only.
    • what it is: a generator that copies one real database. it is trained on that database and samples a synthetic version of it. it is not a prior over many databases. p(database) = p(key graph) · p(attributes | key graph).
    • structure part, the reusable idea: the key graph is sampled from a degree-corrected, nested stochastic block model with hard constraints ("2K+SBM"): fixed number of rows and links per relationship, exact degree sequence, joint degree distribution of linked rows, blocks inside each table found by minimum description length. referential integrity holds by construction.
    • why this matters for a prior: plurel also uses a hierarchical block model for links [plurel-3], but with sampled block probabilities, not with a target degree sequence. my stage 3 statistics give real degree sequences (heavy tail, 40 % childless parents) [stage 3]. a prior can sample a degree sequence from a fitted family first and then wire the links this way. that controls fan-out directly.
    • their figure 2 point: matching degree distributions alone loses the hierarchy of the F1 database; clavaDDPM keeps some hierarchy but not the degrees. both properties are needed.
    • attribute part: joint diffusion over all tables (gaussian for numbers, masking for categories), denoiser = heterogeneous graphsage with transformer encoders per table, each row conditioned on its noisy k-hop neighbourhood. dimension tables are kept as fixed vocabularies.
    • results they report: 11 databases, 67 tables, 64 key links. best on most multi-table fidelity metrics; the drop from single-table to multi-table detection is 7× smaller than for clavaDDPM; best utility on 4 of 5 databases when a GNN is trained on synthetic and tested on real data.
    • they note that fidelity and utility are different: "methods with lower performance on data fidelity sometimes outperform stronger methods on utility". same lesson as plurel's reversal [fr-plurel]: a realism score alone is not a safe way to select a prior.
    • no time model: timestamps are ordinary datetime attributes. no order constraint between parent and child times is stated in the text i read. not checked in the appendix.
  • [fr-grdm] grdm (ketata et al., neurips 2025), read: introduction, background, the full method section (papers/grdm/raw.txt L1-1500). not read: experiment tables, appendix. earlier: abstract only.
    • same family and same factorisation as reldiff [fr-reldiff]: copy one real database; first the key graph, then all attributes jointly by diffusion with a heterogeneous graphsage denoiser (K = 1 hop per step; many steps reach many hops).
    • structure part is simpler than reldiff: take the empirical distribution of children per parent row for each link type, sample children from the root tables down, then merge duplicate nodes by random matching when a table has several parents. it keeps the in-degree distribution only, not the joint degrees or the hierarchy.
    • argument for generating keys before features: with features first, all n × m possible links must be scored. with keys first, only "the number of nodes and their per edge-type degree" must be modelled. plurel and rdb-pfn also do structure before content [plurel-3] [fr-rdbpfn].
    • dimension tables (few rows, each a unique real thing, for example countries) are not generated. they are kept fixed as metadata, like the category set of a categorical column. a prior needs the same split: small fixed lookup tables vs growing fact tables.
    • their criticism of parent-to-child generation: fixed table order, no parallel sampling, and conditional independence of rows given parents, where "small errors can accumulate across generation steps". syntherela measured that effect [fr-syntherela].
    • claim in the abstract: on 6 real databases better than autoregressive baselines on multi-hop correlations. numbers not read.

      • what no corpus gives: realistic row-level dynamics. schemapile has almost no rows, wikidbs has no time. row-level realism must come from relbench, THE JOIN [join-4] or from a model of events.
      • for the task side, there are now three declarative task languages: relarena's RPI, THE JOIN's SQL manifests [join-7], and RTGL. a forecasting-task prior can reuse one of them to define labels on synthetic data, and then its tasks are comparable by construction.
  • [c3] event models for a forecasting-task prior
    • [c3-1] the labels of relbench are functionals of a marked point process. my derivation from [relbench-3] and [formal-5], not from a paper: each fact-table row is an event (time, entity, mark). churn = "zero events of entity e in (t, t+δ]"; count and sum tasks = number of events or sum of a mark in the window; "top 3" or "more than one click" = a threshold on such a count. so a prior over tasks = a prior over event processes per entity + a prior over window functionals [join-6].
    • [c3-2] "buy till you die" models (marketing science; pareto/NBD, BG/NBD). source: wikipedia page "Buy Till you Die" and a search summary; the original papers are not read. two processes per customer: a repeat-purchase process while "alive" (poisson with a personal rate; rates gamma-distributed over customers → negative binomial counts) and a dropout process (pareto type II, or geometric with beta mixing). the wikipedia page cites fader et al. 2005 for BG/NBD. unverified
      • why it fits: it makes exactly the things stage 3 found. zero-inflated counts (dropped-out customers), heavy-tailed activity (gamma rates), entity repetition with persistent rates, and churn as a named quantity [s3-2].
    • [c3-3] a pfn for point processes exists: FIM-PP (berghaus, seifner, cvejoski, ojeda, sánchez; arxiv 2509.24762; iclr 2026 per arxiv). source: arxiv abstract. "we pretrain a deep neural network to infer, in-context, the conditional intensity functions of event histories"; "pretraining is performed on a large synthetic dataset of MTPPs sampled from a broad distribution of Hawkes processes"; zero-shot on real data, or fine-tuned. a search summary adds: 72,000 hawkes processes, 14.4M events, with self-excitation, inhibition, periodicity. unverified. not in the README.
      • it works on event sequences, not on databases: no tables, no keys, no attributes of entities. but its prior over hawkes kernels is a tested recipe for the event side.
    • [c3-4] what the published priors do with time. plurel: trend, cycle and noise on the exogenous inputs, indexed by row number [plurel-4]. rdb-pfn: trend, seasonality, spike on the latent initialisation [rdbpfn-2]. both model how values drift over time. neither models when and how often an entity has events, which is what the labels count.
    • [c3-5] what this means for the prior (my reading). a forecasting-task prior can be small:
      • entities with latent traits (rate, dropout hazard, mark scale) drawn from heavy-tailed distributions; traits depend on entity attributes through a random function, as in tabpfn's SCM.
      • events per entity from a renewal or hawkes process with seasonality and dropout; marks from an SCM conditioned on the entity and on parent rows.
      • tasks = a seed-time grid + a window functional from the THE JOIN vocabulary.
      • then DFS + target-history features, as in relarena, and a pfn on the flat table. every part exists; the combination is not in the papers i read.
      • first test that needs no training: generate such databases, compute the stage 3 statistics on them (zero share, rows per entity, positive rate, fan-out) and compare with [s3-1] [s3-2] and with plurel output.
  • [c4] latest relational / tabular work that can give an edge (round 1; all from arxiv abstracts or search summaries, unverified)
    • [c4-1] "parameter-free encoders remain viable for RDB foundation models" (xu, wipf; arxiv 2607.05476, july 2026). the same group as rdblearn. they "prove theoretical limitations on trainable encoder parameters" when labels are available as inputs, and show that parameter-free encoders (DFS-style) + a single-table foundation model stay strong. relarena cites it as rdblearn v1.1.
      • meaning: a theory argument for the "flatten + TFM" side, and against [dir-4] (learned flattening). it must be read before anyone invests in a trained relational encoder. it also says where a prior can still help: in the tabular model, not in the encoder.
    • [c4-2] relagent (huang, tichelman, kim, olejniczak, ceylan; arxiv 2605.07840, may 2026). an LLM agent writes SQL feature programs and selects a classical model in a search phase; inference runs the program with no LLM. features are "human-readable queries". relarena cites it as evidence that iterative feature engineering helps [relarena-2].
      • meaning: a third way to flatten, next to DFS and relicl: task-specific SQL features found by search. its features are the kind of window aggregates that the THE JOIN labels use [join-6].
    • [c4-3] support-set target leakage in relational ICL (upendra et al.; arxiv 2609.36384, 28 sep 2026; shares authors with rt-j). 14 synthetic "leaker" column types; "target-table leakers cause the clearest degradation, while one- and two-hop leakers are not consistently used by the model". the README has supportsetleakage with id 2609.36417: unverified whether that is the same paper under another id.
      • meaning for us: tabpfn-rel's target-history features and "validation rows as context" are exactly support-side label information. a prior with repeated entities must generate it the leak-free way (labels strictly before the seed time).
    • [c4-4] the field's direction in the last 4 months, from what i read tonight: (1) real data came back: rt-j pretrains on 639 real databases after a synthetic phase [rtj-3], openrfm mixes synthetic and real [openrfm-2]. (2) the harness matters as much as the model: tabpfn-rel gained about 200 Elo from text, hurdle regression, more context and a fixed depth [repo-tabpfnrel-1]. (3) task definition is being standardised (RPI, RTGL, THE JOIN manifests) [c2-5].
    • [c4-5] where an edge can still be (my reading)
      • nobody has shown that a relational prior improves a large tabular model on the full protocol. rdb-pfn showed it for a 0.7M model in the few-shot protocol; tonight's first runs put that model near tabpfn-3 on rel-f1 and far below it on rel-trial [s4-7].
      • the cheapest strong move: continue the pretraining of an open tabular model (tabicl v2 is open; tabpfn weights are non-commercial but usable for research) on DFS-flattened tables with forecasting labels, from a synthetic event prior and / or THE JOIN, and measure it in relarena against the same model without that step. this is [dir-2] + [dir-5] with one model and one switch.
  • [c4-6] xu and wipf, read. pdf in papers/parameterfreeencoders/, read with pdftotext: abstract, §3, §4, §5, §6 (not the proofs in app. D).
    • proposition 3.1 (§3): for any ego-network with past labels in it, distributions exist where the label is a deterministic function of the database, "and yet any possible fixed encoder … and prediction head … perform no better than chance". so a frozen trainable encoder has no stable rule for how to use neighbourhood labels across tasks. a per-task supervised model can learn one.
    • their reading of why RT still works: in the few real databases used for pretraining, homophily dominates, so "adopting the majority label of local neighbors" is already strong. they cite RT's own table: an entity-mean predictor has 66.7 average AUROC against 69.7 for RT.
    • proposition 4.1 (§4): distributions exist where the labels in the neighbourhood "provide no information" about which feature columns are informative. so labels as encoder inputs do not reliably help to screen columns.
    • they are careful: "while not strictly ruling out any benefit of trainable encoders", it "does mute confidence".
    • empirical part (§5, fig. 1): an updated rdblearn "outperforms all open-source FMs on all benchmarks, and even exceeds closed-source FMs on 4 of 6 benchmarks", "with no task-specific adjustments and zero exposure to RDB data".
    • take-home (§6): "parameter-free RDB encoding combined with frontier single-table FMs is still competitive with the best closed-source industry architectures".
    • meaning for us: these are existence results (worst-case distributions), not claims about typical data. they agree with tonight's numbers: per-entity label history is the dominant feature on user-ignore [s4-9], and DFS + a single-table model is level with or ahead of relational models. the paper puts the open room in the single-table model and its prior, which is where steps 1 and 2 of [dir-update] work.
