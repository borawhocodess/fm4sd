1 · The relational problem

Why one table is not enough

  • A tabular model needs one row with a fixed number of columns.
  • A customer has 0, 3 or 3000 transactions: a set, not a vector.

Flatten

  • Aggregate linked rows into columns.
  • Then use a tabular model.
  • Can lose: signal beyond the depth limit.
  • Can lose: interactions between columns.

Keep the structure

  • Rows are nodes, key links are edges.
  • Learn on the graph.
  • Cost: one trained model per task,
  • or a pretrained relational model.

On the real benchmark, flattening is still competitive.

log: relicl-1, relarena-4

The two losses of flattening are shown by RelICL on synthetic tasks. RelArena shows that flattening plus TabPFN-3 is first among models with standard tuning.

2 · Formal definition

The database

(𝒯, ℒ)

  • Tables 𝒯 = {T₁, …, Tₙ}
  • Links ℒ ⊆ 𝒯 × 𝒯
  • (T_fkey, T_pkey) ∈ ℒ: a foreign key of T_fkey
  • points to the primary key of T_pkey.
  • A table is a set of rows. A row is an entity.

v = (pᵥ, 𝒦ᵥ, xᵥ, tᵥ)

pᵥprimary key
𝒦ᵥforeign keys
xᵥattributes, same columns per table
tᵥtimestamp, optional

Notation of Fey et al. 2023, §2.1; the RDL survey uses the same symbols · log: formal-1, formal-2

This is the notation of the relational deep learning position paper. A link exists if a foreign key column of one table points to the primary key of another. RelBench describes the same objects in words.

2 · Formal definition

The task is one more table

T_train: v = (𝒦ᵥ, tᵥ, yᵥ)

  • 𝒦ᵥ: which entity the example is about
  • tᵥ: when the prediction is made (seed time)
  • yᵥ: the label
  • No inputs xᵥ here. The input is the database.

To predict yᵥ, use only entities u with tᵤ ≤ tᵥ.

training table (example)

  • Labels come from the database itself:
  • an SQL query over the window [t, t + δ],
  • repeated for earlier t.

Fey et al. 2023, §2.2 · the table rows are an invented example · log: formal-3 to formal-6

The training table has no input attributes; the input is the database. The same customer appears at several seed times. RDBLearn uses strictly earlier, t_u less than t_v; RelArena notes that this boundary is not standardized.

2 · Formal definition

Two ways to learn, and what flattening is

Trained per task

f_θ(x_test, RDB) ≈ y_test

Fit θ on the training table of this task.

In-context

y_test = f_θ(x_test, D_ICL, RDB)

D_ICL = {(xᵢ, yᵢ)}: labelled examples. No training.

Flattening is a fixed function g of the neighbourhood

u = g(N_RDB(x)) · z = [x; u] · y_test = f_θ(z_test, D_ICL of z)

The database reaches the model only through g.

Notation of RDBLearn §2–3 · log: formal-7

In-context: no training on the task; the labelled examples are part of the input. g is not learned. This is the point where a learned or prior-matched flattening would enter.

Every task is a next-window question

  • amazon/user-churn: no review in the next 3 months
  • f1/driver-top3: qualifies top 3 in the next month
  • hm/item-sales: total sales in the next week
  • trial/study-adverse: adverse events, next year

Split by time

  • validate: between the two cutoffs
  • test: after the test cutoff
  • task size: 1,353 to 4.7M training rows

What RelArena found when it re-ran the methods

  • Two evaluation regimes; on rel-f1 they differ by 10+ AUC points.
  • Label leak in rel-event, fixed 2026: old scores 2–6 points too high.
  • Tuning effort differs and is often not documented.
  • Each paper aggregates regression results differently.

Robinson et al. 2024; Hayler et al. 2026, §1 · log: relbench-6, relarena-2

The LightGBM baseline uses the entity table only, so it is a weak stand-in for tabular methods. Regime one freezes the database at the test cutoff for all test rows. Regime two lets each test row see data up to its own timestamp. Only rel-f1 has test timestamps that span years. The leak was in rel-event/user-ignore.

4 · TabPFN-Rel

Flatten the database, then predict in-context

1 · Database + training table

Tables, key links, and one row per (entity, seed time, label).

2 · Deep feature synthesis

Aggregate along all key paths up to depth d, before each row's cutoff.

3 · One flat table

Plus calendar features and past labels of the same entity.

4 · TabPFN-3, in-context

Train rows are the context. Test rows are the queries.

  • Prior Labs' harness around TabPFN-3. No relational model is trained.
  • Lineage: featuretools (DFS) → RDBLearn → TabPFN-Rel.

Hayler et al. 2026, §2.2 and code · log: tabpfnrel-1, tabpfnrel-3

In the formal view of slide 6, deep feature synthesis is the fixed function g and TabPFN-3 is f. Each row only sees data before its own cutoff time.

4 · TabPFN-Rel

The settings

PartSetting
DFS depth d2, 3 or 4, chosen on validation. The only tuned value.
DFS enginefastdfs, SQL on DuckDB. Computed once at depth 4, cut down for 2 and 3.
Time columnsTurned into "time before the cutoff".
Text columnsDropped. The API version re-attaches the entity table's text.
Added featuressin/cos of month, weekday, day of year; lags of the entity's past labels.
Context8 estimators; each draws 100,000 rows from the 400,000 most recent.
Test timeValidation rows are added to the context.

Against RDBLearn: TabPFN-3 only, 10× more context rows, recency-aware context, text columns.

Paper + relarena code · aggregation list not confirmed yet · log: tabpfnrel-2, tabpfnrel-3

One more change against RDBLearn: the tuning split is frozen at the val cutoff. RDBLearn's default aggregations are max, min, mean, count, mode, std. It is not yet confirmed that TabPFN-Rel uses the same list.

4 · TabPFN-Rel

Results on RelArena, and the limits

Results

  • RelArena: 21 RelBench entity tasks, one harness, Elo.
  • TabPFN-Rel: first with the standard tuning regime.
  • August paper: RT-PluRel first overall (fine-tuned).
  • Repo today: a newer TabPFN-Rel is first overall.
  • Each entity's past average beats 2 GNNs on 4 tasks.

Limits the authors state

  • One seed.
  • DFS takes CPU hours; not in the runtime table.
  • Tuning the depth helps on 9 of 21 tasks.
  • Without text: Elo 1821 → 1706, from two tasks.
  • Timestamp boundary differs between methods.
  • No boosted trees on DFS features yet.

Hayler et al. 2026 · log: relarena-4 to relarena-9, s2-6

Leaderboard in the repo on 5 Oct 2026, models plus systems: TabPFN-Rel client latest 1992, local latest 1941, RT-PluRel 1879. RelArena uses one evaluation regime for all methods. RT-PluRel is a relational transformer pretrained on synthetic databases; it is a system submission with its own tuning, up to 50,000 fine-tuning steps per task. The constant predictor returns each entity's own past average and beats RelGNN and RelGT on 4 tasks each. The two text tasks are rel-event/user-ignore and rel-avito/user-clicks.

5 · Related work

Each method changes a different part

RDB-PFN

New prior, same DFS

  • Synthetic DBs → DFS → 6-layer PFN
  • Binary classification only
  • Context ≤ 1024 rows, 30 columns
  • Few-shot tests only
  • DFS choice: AUC 0.57 → 0.73

RelICL

New flattening, same TFM

  • No training, no depth limit
  • Sees column interactions
  • Claims par with TabPFN-Rel
  • Baselines not re-run

PluRel → RT

New model, new prior

  • First overall in the August paper
  • Needs fine-tuning per task
  • Synthetic-only: "lazy" regime

log: rdbpfn-1, -4, -6, -7 · relicl-2, -4 · relarena-4 · openrfm-1

RDB-PFN: not tested in the full RelBench protocol; its own ablation shows DFS settings move the average AUC from 0.57 to 0.73; its schema generator is trained on real schemas; its released config has width 96 while the paper says 128. RelICL: its comparison uses numbers copied from the papers. The lazy regime is OpenRFM's finding about synthetic-only pretraining of RT.
